# 12 — v1.1: Store builder additions (F15–F18)

Status: specified 2026-10-01, after the MVP (F00–F14) was built. This document holds every cross-cutting change for F15–F18: decisions, data model, Shopify operations, AI schemas, routes, limits and compliance rules. The feature specs in `docs/specs/F15`–`F18` reference the sections below. Where this document changes an earlier document, the earlier document carries a one-line pointer to the section here.

Background: competitors such as Storecraft (Shopify App Store, launched 28 Sep 2026) create a whole store from a short description: brand name, catalogue, collections, menu and standard pages. Mosaiq adds a second onboarding route that does this, without becoming a sourcing or fulfilment app.

## 1. Decisions

| # | Decision | Reason |
| --- | --- | --- |
| D-15.1 | "Start from zero" is a **second route** next to the existing onboarding. The existing route (merchant already has a brand and products) does not change. | Merchants with a brand should not go through a name generator. |
| D-15.2 | Mosaiq does **not** source products, place supplier orders or fulfil orders. Products still come in through the merchant's dropship/POD app (DSers, CJ, Zendrop, AutoDS, Printify) or manually. | Fulfilment is the core of those apps; building it means supplier lock-in and high maintenance. 06 ownership rules stay in force. |
| D-15.3 | Mosaiq never overwrites the merchant's `main-menu`. It creates its own menu with handle `mosaiq-main` and guides the merchant to select it in the theme header. | Menus are merchant-owned; overwriting is destructive and cannot be undone by Shopify. |
| D-15.4 | Mosaiq never invents business facts: address, company registration, VAT ID, phone, delivery times, shipping costs, return address. These come from `BusinessDetails` (§2.1) and `DeliveryProfile` (§2.4). Missing facts block go-live of the page that needs them. | Invented facts are misleading commercial practice and break 07. |
| D-15.5 | Shopify store policies (`shopPolicyUpdate`) stay merchant-owned. Mosaiq creates normal pages and shows policy text the merchant can paste. No `write_legal_policies` scope. | Minimal scopes (03 §1). |
| D-17.1 | The price advisor only **writes** prices on products Mosaiq may write (`sources.guards.assert_writable` passes for price, i.e. not managed by a sync app, 06 §3). For sync-app products it shows the advice and tells the merchant where to set it. | 06 ownership matrix. |
| D-18.1 | Delivery estimates are merchant-supplied defaults per source app plus product overrides. Mosaiq does not read supplier warehouses. | No reliable warehouse data via Shopify (06 §4). |

## 3. AI schemas (add to `apps/ai/schemas.py`)

```python
Market = Literal["NL", "BE", "DE", "AT", "FR", "LU", "GB", "IE", "OTHER_EU"]
PriceLevel = Literal["budget", "mid", "premium"]


class NicheBrief(BaseModel):
    description: str = Field(min_length=20, max_length=500)  # merchant's own words
    markets: list[Market] = Field(min_length=1, max_length=5)
    content_locales: list[Locale] = Field(min_length=1, max_length=3)
    audience: str = Field(max_length=200)
    price_level: PriceLevel
    import_app: Literal["dsers", "cj", "zendrop", "autods", "printify", "printful", "manual", "other"]


class NameIdea(BaseModel):
    name: str = Field(min_length=3, max_length=14, pattern=r"^[A-Za-z][A-Za-z0-9]*$")
    rationale: str = Field(max_length=160)
    pronunciation_ok: list[Locale]  # locales in which it reads naturally


class NameSuggestions(BaseModel):  # tool submit_names
    names: list[NameIdea] = Field(min_length=8, max_length=8)


class BrandProposal(BaseModel):  # tool submit_brand
    tone: Literal["warm", "premium", "playful", "clinical", "sporty"]
    style_preset: Literal["clean", "bold", "organic", "luxe", "tech", "soft"]
    palette: PaletteSuggestion  # existing schema (05 §3); contrast re-checked in code (F05-3)
    font_heading: str  # key from themes/fonts.py; validated against the list
    font_body: str
    tagline: str = Field(max_length=60)
    rationale: str = Field(max_length=240)


class ProductIdea(BaseModel):
    title: str = Field(max_length=80)
    why: str = Field(max_length=200)
    search_phrases: list[str] = Field(min_length=2, max_length=4)  # to paste into the import app
    target_price_band: str = Field(max_length=30)  # e.g. "€25–35 incl. VAT"
    eu_notes: list[str] = Field(max_length=4)  # e.g. "CE marking required", "no medical claims"


class ProductIdeas(BaseModel):  # tool submit_product_ideas
    ideas: list[ProductIdea] = Field(min_length=5, max_length=10)
    avoid: list[str] = Field(max_length=6)  # product types to avoid in the EU for this niche


class CollectionPlan(BaseModel):
    title: str = Field(max_length=60)
    description: str = Field(max_length=300)
    product_gids: list[str] = Field(min_length=1, max_length=20)  # subset of selected_product_gids


class MenuItemPlan(BaseModel):
    title: str = Field(max_length=40)
    target: Literal["frontpage", "collection", "page", "catalog"]
    ref: str | None = None  # collection title or page_type; resolved to a GID at build time


class StoreStructure(BaseModel):  # tool submit_structure
    collections: list[CollectionPlan] = Field(min_length=1, max_length=6)
    menu: list[MenuItemPlan] = Field(min_length=3, max_length=8)
    pages: list[Literal["about", "faq", "shipping", "returns"]] = Field(min_length=2, max_length=4)


EditOpKind = Literal["replace_field", "add_section", "remove_section", "move_section"]


class EditOp(BaseModel):
    op: EditOpKind
    section_index: int = Field(ge=0, le=13)
    field: str | None = None  # replace_field only; dotted path inside the section, e.g. "items.1.text"
    value: str | None = Field(default=None, max_length=1200)  # replace_field only
    section: Section | None = None  # add_section only (existing discriminated union, 05 §3)
    to_index: int | None = Field(default=None, ge=0, le=13)  # move_section only


class PageEditResult(BaseModel):  # tool submit_page_edit
    operations: list[EditOp] = Field(min_length=1, max_length=10)
    summary: str = Field(max_length=200)  # shown to the merchant, in the UI language
```

Validation rules after the schema (code, not AI):
- `replace_field`: the path must exist in the section, the new value must satisfy the field's own `max_length` (the section model is re-validated after applying), and the field must not be in `EDIT_LOCKED_FIELDS` = `type`, `image_slot`, any key starting with `price`, `offer`, `gpsr`, `unit_price`, `prior_price`.
- `add_section`: the resulting section list must still match the allowed types and maximum count for the page type (05 §4.3 table); `specs` and `guarantee` follow their existing conditions.
- `remove_section`: never `hero` on `pdp`/`home`/`landing`; the minimum of 2 sections stays.
- Any failure → the whole edit is `failed` with code `EDIT_INVALID`; nothing is applied.

Section rules for the new page types (extend the 05 §4.3 table):

| `page_type` | sections |
| --- | --- |
| `faq` | rich_text (intro), faq (8–12 items) |
| `shipping` | rich_text (intro), rich_text (delivery times — **rendered from `DeliveryProfile`, not written by AI**), faq (3–6 items) |
| `returns` | rich_text (summary of the 14-day withdrawal right with a link to the withdrawal page of 07 §7), rich_text (return address and process from `BusinessDetails`), faq (3–5 items) |

For `shipping` and `returns` the AI writes only intro and FAQ text; the code inserts the factual blocks from the models. The prompt receives the facts and the instruction "Do not state numbers, costs, addresses or time frames other than those given".

- **App-data / product metafields:** PRODUCT metafield `$app:mosaiq` key `delivery` (type `json`): `{"min_days":8,"max_days":14,"ship_from":"CN","by_market":{"NL":[8,14],"DE":[9,15]}}`, written when profiles or overrides change (Celery task `compliance.tasks.sync_delivery_metafields`, batched with `metafieldsSet`, max 25 per call).

## 5. Pipeline additions (05)

- `kind = store_build` (F15): the parent job does no AI work itself. It creates, in order:
  1. Collections (`collection_create`, unpublished), stored as `ManagedResource`.
  2. One child `page` job per standard page type in `StoreStructure.pages` and one `home` job, all sharing the blueprint's brief as `niche_hint`/context.
  3. One child `pdp` job per selected product (`kind=page`, `page_type=pdp`, `product_gid`). PDP jobs may run in parallel (max 3 concurrent per shop, Celery queue `generation`).
  4. Menu (`menu_create`) once all page jobs have a Shopify page GID.
  The parent succeeds when all children succeed; a failed child does not roll back the others; the blueprint shows per-item status with "Retry".
- Prompts: `docs/prompts/niche_names.md`, `niche_brand.md`, `product_ideas.md`, `store_structure.md`, `edit_page.md`. Model per prompt is given in the file. These calls are small and do not count as generations.
- The `copy` step for `pdp` receives the delivery estimate (§2.4) for the shop's first market, and the guardrail "Do not promise faster delivery than {{ max_days }} working days; never say 'fast shipping' if max_days > 5".
- New error codes: `EDIT_INVALID` (edit could not be applied), `SCOPE_MISSING` (new scope not granted), `BLUEPRINT_NO_PRODUCTS` (no products selected), `BUSINESS_DETAILS_MISSING` (page needs facts that are missing). NL/EN merchant texts in the error table as for the others.

| Limit | `starter` | `pro` | `agency` |
| --- | --- | --- | --- |

| Products per store build | 5 | 20 | 20 |

A store build reserves `store_generations = 1 + max(0, n_pdps − 1)` and `ai_images` for all PDPs at the start (same reservation rules as 05 §5). If the plan has too little left, the build screen shows how many products fit and lets the merchant deselect.

## 8. Compliance additions (07)

- **Delivery information (CRD art. 6(1)(g); NL art. 6:230m BW; DE Art. 246a EGBGB):** the product page must state the delivery time before purchase. When a `DeliveryProfile` or override applies, `mq-price` renders "Delivery in {min}–{max} working days (ships from {country})" per market. If no estimate exists for a product, the product's compliance checklist shows "Delivery time missing" (warn, not block, because the merchant may state it in the theme).
- **30-day rule (CRD art. 18):** if `max_days > 30` for any market, block go-live of the product page with `DELIVERY_OVER_30_DAYS` and explain that delivery beyond 30 days needs explicit agreement.
- **Cut-off notice (07 §3):** the existing "order before 16:00, delivered tomorrow" notice is suppressed on any product whose estimate has `max_days > Shop.ship_cutoff.delivery_days`.
- **New claim rule `SHIPPING_CLAIM`** (07 §4.1 table, severity `block` when contradicted by data, else `warn`): phrases about fast delivery (nl: "snelle levering", "morgen in huis", "binnen 24 uur"; en: "fast shipping", "next-day delivery", "ships in 24 hours"; de: "schnelle Lieferung", "morgen geliefert", "Lieferung in 24 Stunden") are `block` when the product's `max_days > 3`, `warn` when no estimate exists. "Ships from EU / EU warehouse" claims are `block` unless `ship_from_country` is an EU member state.
- **Brand names (F15):** suggested names must pass the 07 §4.1 blocklist (no generic environmental claims such as "eco", "green", "bio" unless the merchant confirms certification; no health claims; no geographic origin claims such as "Swiss" or "Dutch" unless true), and must not equal a name on `themes/brand_blocklist.py` (well-known brands; start with the top 500 consumer brands, maintained as data).
- **Price advisor and Omnibus:** when the advised price is higher than the current price, show: "If you raise the price now and discount it later, the strikethrough price must be the lowest price of the 30 days before the discount (07 §1)." Applying a price creates a `PriceHistory` row via the existing `products/update` webhook; no extra code.
